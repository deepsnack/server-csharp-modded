# Mod 服装检索与事务发放代码审查报告

日期：2026-07-22  
范围：SPT 4.0.13 自定义 Core / BattlePass / Tarkov-1.0-Backport 运行时兼容  
结论：两轮独立复审发现的分类、事务与并发阻断均已收口；Release 构建和 7 项定向测试通过，未发现剩余 P0/P1。

## 根因

- 原搜索路径没有把运行时 customization、trader suits 和全部 locale 统一成 suite 目录，Mod 注入服装可能只能用某个语言或某个内部组件 ID 命中，返回值也可能混淆 suite、outfit offer 与 body/hands component。
- 仅凭 Body/Feet 字段判断会把原版 `Type=Node` 分类节点当成可发放套装；反向地，若 trader offer 可绕过结构校验，`Type=Item` 的 BODY/FEET/HANDS component 也会冒充 suite。
- 无效、未知或 component clothing reward 旧路径会静默跳过，外层仍可把等级、循环或补偿账本标为已领取。
- entitlement 原先先改内存并通知客户端，档案保存失败仍可能落 claimed；补偿领取还使用独立锁，可与普通领取并发并让失败回滚误删另一请求的成功 entitlement。

## 目录与搜索审查

- 新 `BattlePassClothingCatalogService` 每次调用读取实时 customization/trader 数据，能看到 Mod 在 PostDB 阶段注册的服装，不缓存过早快照，也不依赖 Backport 程序集。
- 可发放候选必须同时满足 `Type == Item` 与合法 suite 结构：Parent 为 UPPER/LOWER，或 Parent 为 SUITS 且带 Body/Feet 组件引用。Trader offer 只补充 offerId/traderId/active 元数据，不能绕过结构规则。
- 搜索别名包含 suiteId、outfit offerId、traderId、Body/Feet/Hands tpl、属性文本以及所有已注册 locale 的名称/短名/描述；结果 `Id/SuitId` 始终是 suiteId。
- 名称解析不再把 offer/trader locale 当服装名称候选，避免无本地化服装显示 Ragman 描述；offerId/traderId 仍可用于查找。
- 命中项先按相关度、显示名、suiteId 稳定排序，再执行 1–100 的 limit。

## 发放、持久化与并发审查

- 整批奖励在任何邮件、钱包、称号、购买权或档案副作用前预校验所有 clothing ID；空值、非法 MongoId、未知 ID、Node 或 component 都使领取返回可重试失败。
- 本次新增 clothing/recipe 先写入 profile 内存批次并保存；保存失败时只回滚本批新增 ID，再尝试持久化回滚。成功保存后才发送 `CustomizationUpdateRequired`。
- 刷新通知失败不会把已持久化 entitlement 变成失败领取；客户端下次正常刷新仍会得到服装，避免重复其他奖励。
- Claim、ClaimCycle、ClaimCompensation 与公开 GrantRewards 的奖励变更、保存、通知和回滚共用 `BattlePassStore.LockProfile(profileId)`；同 profile 串行，不同 profile 仍并行。
- 领取状态保存使用快照事务：claimed free/premium/cycle、reward ledger、ledger initialized 和 purchase rights 在写盘失败时恢复缓存，并再次尝试保存恢复状态。普通等级、循环与补偿只在 Grant 成功后提交 claimed/ledger。
- 测试用固定 Backport suite/top/hands、Ragman offer 列表、en/ch LazyLoad、通知队列和测试档案均在 finally 中恢复或清理，不污染共享 DI 单例。
